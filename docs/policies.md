# 도메인 정책 (policies.md)

> 차감·예약·상태에 관한 모든 규칙의 최종 기준 문서.
> 코드 구현이 이 문서와 다르면 코드가 틀린 것이다.

## 1. 이용권 3종

| 이용권        | 코드                 | 결제 단위     | 이용 방식                                         |
| ------------- | -------------------- | ------------- | ------------------------------------------------- |
| 저녁반 회비   | `EVENING_MEMBERSHIP` | 1 / 3 / 6개월 | 기간 내 저녁반(단체수업) 무제한 참여, 예약 불필요 |
| 예약제 횟수권 | `SESSION_PASS`       | 횟수          | 예약제 수업(SESSION)을 예약해 참여, 1회 차감      |
| 1:1 레슨권    | `LESSON_PASS`        | 횟수          | 1:1 레슨(LESSON)을 예약해 참여, 1회 차감          |

- 모든 결제는 오프라인. 관리자가 시스템에 수기 등록한다.
  - 등록 시 **시작일을 지정할 수 있다** (기본값 오늘, 과거 날짜 허용) — 수기 등록이라 결제·이용 시작 시점과 등록 시점이 다를 수 있다 (D-055)
  - 횟수권 초기 횟수는 **0.5 단위 자유 입력**. 초기 부여도 `INITIAL_GRANT` 이력으로 남는다 (D-055)
- 한 회원이 여러 이용권을 동시 보유할 수 있다.
- `SESSION_PASS`, `LESSON_PASS` 유효기간: **시작일로부터 1년** (D-055).
  관리자가 유효기간을 수정할 수 있다 — 만료 후 서비스 부여 등 대응 (D-056)
- `EVENING_MEMBERSHIP` 기간(1/3/6개월)은 **시작일 기준**으로 계산하며, 관리자가 수정(연장)할 수 있다 (이벤트, 휴회 보상, 추가 결제)
- 유효기간·회비 기간의 **종료일은 그 날짜 당일까지 사용 가능**하다 — `endDate = startDate.plusYears(1)/plusMonths(개월수).minusDays(1)`, 유효 판정 `!today.isAfter(endDate)` (D-066)
- 기간·유효기간 변경은 **변경 전값/후값/사유/주체/시각**이 `PassPeriodChange` 이력으로 남는다 (D-057)
- **오등록 정정**: 관리자가 이용권 등록을 취소할 수 있다 — 물리 삭제가 아닌 **취소 상태 전환** + `REGISTRATION_CANCELED` 이력(횟수권은 잔여를 0으로 상쇄).
  취소된 이용권은 회원 화면에서 숨기고, 관리자 화면에서는 구분 표시한다 (D-059)
- **등록 취소 선행 조건**: 그 이용권으로 잡힌 **활성 예약이 하나라도 있으면 등록 취소를 거부**한다 (D-089).
  관리자가 예약을 먼저 정리(대리 취소 — 이 경우 복구 없이)한 뒤 등록을 취소한다.
  자동 연쇄 취소는 만들지 않는다 — 오등록 정정은 드문 운영 행위이고, 취소된 이용권의 잔여는
  0으로 상쇄되므로 연쇄 복구가 곧바로 상쇄와 충돌한다. 명시적 2단계 절차가 안전하다.

## 2. 시간표 (송파점 기준)

- 모든 타임은 **90분** 단위
- 저녁반: 월~금 19:00–20:30, 21:00–22:30
- 예약제 수업: 화·목·금 11:00–12:30, 13:00–14:30 / 토·일 09:00, 11:00, 13:00, 15:00, 17:00 시작 5타임
- **1:1 레슨**: 저녁반·예약제 수업이 열리는 모든 타임(주 26타임)에 예약 가능.
  저녁반·예약제 수업과 **같은 타임에 동시 진행 가능** (코치 2명 체제).
  단, 1:1은 **타임당 1명**만 예약 가능.
- **정기 시간표 외 임시 세션은 v1에서 허용하지 않는다** (D-146). 날짜별 수업(`ClassSession`)은
  반드시 `시간표의 요일 == 그 날짜의 요일`인 조합으로만 만들어진다 — 보강 수업·임시 수업처럼
  "열리지 않은 요일에 수업을 여는" 운영은 v1 범위 밖이며, 요일이 어긋난 조합의 예약·출석·휴강
  요청은 예약 경로와 같은 판정으로 거부한다(`ClassScheduleNotFoundException`, 404).
  필요해지면 시간표를 먼저 추가한 뒤 그 시간표로 처리한다.

## 3. 예약 규칙

- **오픈**: 해당 주 월요일에 그 주(월~일) 전체 예약이 열린다. 다음 주 예약은 불가.
- **마감**: 수업 시작 시각 전까지 예약 가능 (별도 마감 없음)
- **정원**: 예약제 수업 10명 (지점/수업별 설정 가능하게 구현), 1:1 레슨 1명
- **회원의 취소/변경**:
  - 취소 = 예약을 **취소 상태로 전환** + 차감 복구 (D-090). 예약 행을 지우지 않는다 —
    "누가 언제 어떤 수업을 취소했는지"가 남아야 하고, 감사 가능성은 이 프로젝트의 핵심 가치다.
    취소한 타임을 같은 회원이 다시 예약하는 것은 허용한다
  - 변경 = 기존 예약 취소 + 다른 타임 재예약으로 처리. **하나의 트랜잭션으로 처리**해
    재예약이 실패하면(정원 초과 등) 기존 예약도 그대로 유지된다 (D-090)
  - **당일에는 취소도 변경도 불가** (변경 허용 시 당일취소 우회 가능하므로)
- **관리자의 취소/변경**: 당일 포함 제약 없음. 취소 시 차감 복구 여부 선택 (기본: 복구)
- **노쇼**: 별도 처리 없음 — 예약 시 이미 차감되었으므로 그대로 확정. 출석 기록에만 불참으로 남는다.
- **잔여 부족**: 잔여 횟수가 차감량보다 적으면 예약 자체가 불가 (잔여 0.5회로는 1회짜리 예약 불가)
- **차감 대상 이용권**: 같은 종류 여러 장 보유 시 유효기간 만료가 가장 임박한 한 장에서 차감하고,
  여러 장을 합산해 한 건을 예약할 수 없다 (D-091)
- **유효기간 판정 기준일**은 예약일이 아니라 **수업날**이다 (D-091)
- **같은 회원이 같은 날짜·같은 시각에 두 건을 예약할 수 없다** (D-092)
- **예약 창**: 해당 주 월요일 00:00(`Asia/Seoul`) 오픈, 수업 시작 시각 전 마감, 조회는 이번 주 + 다음 주 2주치 (D-095)

## 4. 차감 규칙

### 4.1 즉시 차감 원칙

- **예약 성공 시 즉시 1회 차감. 취소(회원 당일 전 취소, 관리자 취소-복구 선택, 휴강)로 예약이 사라지면 즉시 복구.**
- 회원이 보는 잔여 횟수는 항상 실제 사용 가능 횟수와 일치해야 한다.
- 모든 차감/복구는 이력 테이블에 기록: (이용권, ±수량, 사유 코드, 발생 주체, 시각)
  - 사유 코드 예: `RESERVE`, `CANCEL_REFUND`, `ADMIN_ADJUST`, `EVENING_HALF`, `INACTIVITY`, `CLASS_CANCELED_REFUND`, `INITIAL_GRANT`, `REGISTRATION_CANCELED`

### 4.2 저녁반 0.5회 참여 (횟수권 회원)

- `SESSION_PASS` 보유 회원은 **0.5회 차감으로 저녁반 참여** 가능
- 사전 예약 불필요. 현장 확인 후 **관리자가 수동으로 0.5회 차감**한다.
- 잔여 0.5회면 저녁반 0.5회 참여만 가능
- 저녁반 출석 추가와 0.5회 차감은 **한 트랜잭션**이며 서버가 판정한다(D-128)
- 수업날 기준 유효한 `EVENING_MEMBERSHIP`을 보유하면 **차감하지 않는다**(회비 우선)
- 회비가 없으면 `SESSION_PASS`에서 0.5 차감한다. 차감 대상 선택은 D-091(만료 임박순·합산 금지)을
  그대로 따르고, **유효기간 판정 기준일은 오늘이 아니라 수업날**이다(소급 입력 대응)
- 회비도 없고 `SESSION_PASS` 잔여가 0.5 미만이면 **출석 추가 자체를 거부**한다 — 관리자가
  수동 가감(§4.2a)으로 충전한 뒤 재시도한다
- 같은 회원이 같은 `ClassSession`에 두 번 출석할 수 없다(회원×세션 유니크) — 이중 차감의 구조적 방지
- 저녁반 출석을 삭제하면 연결된 차감을 `EVENING_HALF_REFUND` 사유로 **자동 복구**한다

### 4.2a 관리자 수동 가감 (ADMIN_ADJUST — D-056)

- 가감 단위는 **0.5**, 사유 입력 필수
- **결과 잔여가 음수가 되는 가감은 거부**한다
- 유효기간이 **만료된 횟수권에도 가감 가능** — 유효기간 수정 기능과 세트로 만료 후 서비스 부여에 대응
- 기간제(`EVENING_MEMBERSHIP`)는 횟수 가감 대상이 아니다 — 기간 수정으로만 조정

### 4.3 2주 미사용 자동 차감 (SESSION_PASS 대상)

- **판정은 회원 단위**다 — 기준일로부터 **2주 경과 시 1회 차감, 이후 2주마다 반복** (4주 미사용 = 2회)
- 기준일: 다음 중 **가장 최근 날짜** (D-027, D-105로 확장)
  - 마지막 출석일
  - 마지막 예약의 수업일 — **취소되지 않은 예약만**, 수업 종류(SESSION/LESSON) 무관
  - `휴회(ON_LEAVE)`에서 **벗어난 시각**(어떤 상태로 나가든) — 휴회가 끝나면 2주 유예가 새로
    시작된다. `ON_LEAVE→ACTIVE` 직행만 기록하면 `ON_LEAVE→INACTIVE→ACTIVE` 같은 운영 경로에서
    휴회 기간이 소급 차감된다(CR-04)
  - `SESSION_PASS` **등록일** (시작일이 아니라 등록일 — 과거 시작일 등록(D-055)이 소급 차감으로 이어지지 않도록)
  - 마지막 **양(+) 수동 가감일**(`ADMIN_ADJUST`) — 충전 시점부터 2주 유예가 새로 시작된다
  - 근거: 출석은 관리자 수동 참고 데이터라 체크 누락 시 부당 차감이 발생할 수 있고,
    예약은 이미 차감된 '사용'이므로 미사용으로 간주하면 모순이다. 복귀일·+가감일은
    **"차감 제외 기간에는 부채가 쌓이지 않는다"** 는 원리의 구현이다
- **차감은 한 번에 한 장**: 차감 가능한 `SESSION_PASS`(취소·만료 아님, 잔여 > 0) 중
  유효기간 만료가 가장 임박한 한 장에서 1회 차감한다 (D-091의 선택 규칙 준용)
  - **잔여가 차감량보다 적으면 잔여만큼만 차감한다** (잔여 0.5 → 0으로 차감) — "잔여 0 제외"
    예외와 연속되는 규칙. 부족분을 다른 장에서 마저 차감하지 않는다 (합산 금지, D-091과 일관)
- 예외 (차감하지 않음):
  - 회원 상태가 `휴회(ON_LEAVE)`인 기간
  - 잔여 횟수 0
  - 유효기간(1년) 만료된 이용권
- **정책 시행일 이전의 미사용은 차감하지 않는다** — 기준일이 정책 시행일보다 이르면 **시행일을
  기준일로 본다**. 시행일은 설정값이며 기본 `2026-09-01`이다 (D-119).
  근거: 아래 캐치업은 "배치가 이미 돌고 있었다"는 전제 위의 설계라, 하한이 없으면 **배치가 아예
  없었던 과거 전체**가 차감 부채로 계산된다 — 200일 전 등록되고 한 번도 쓰이지 않은
  `SESSION_PASS`는 배포 후 첫 실행에서 잔여가 0이 될 수 있다
- **한 번의 배치 실행에서 회원 1명당 최대 1회만 차감한다** — 밀린 주기는 다음 실행들이
  이어받는다(캐치업 유지). 상한은 설정값이며 기본 `1`이다 (D-119).
  근거: 매일 도는 배치에서 정상 부족분은 0 또는 1이고 2 이상은 사고다. 하루 1회로 묶으면 사고가
  나도 피해가 하루 1회씩만 누적돼 관리자가 배치를 멈출 시간이 생긴다
- 구현: **매일 새벽 배치**. 반드시 멱등하게 — "현재 존재해야 할 차감 수 − 기준일 이후 실제
  `INACTIVITY` 이력 수"의 부족분만 채우는 **상태 기반** 계산으로, 같은 날 중복 실행돼도
  이중 차감이 없고 배치가 며칠 밀리면 다음 실행들이 밀린 주기를 이어받아 차감한다 (D-106).
  위 1회 실행 상한은 이 캐치업의 **속도**만 늦추고 **총량**은 바꾸지 않는다.
  (예약 관련 차감은 §4.1의 실시간 트랜잭션, 정책성 차감은 배치로 역할 분리)

## 5. 회원 상태

| 상태     | 코드       | 설명                                                                  |
| -------- | ---------- | --------------------------------------------------------------------- |
| 승인대기 | `PENDING`  | 카카오 가입 직후. 승인 대기 화면만 노출                               |
| 활성     | `ACTIVE`   | 정상 이용                                                             |
| 휴회     | `ON_LEAVE` | 관리자가 설정. 2주 미사용 차감 정지. 저녁반은 기간 연장으로 별도 보상 |
| 비활성   | `INACTIVE` | 탈퇴/장기 미이용 등                                                   |

### 5.1 가입·온보딩

- 카카오 로그인은 **인증 수단으로만** 사용한다 — 기본 제공 정보만 받는다 (실명·전화번호는 카카오에서 수집하지 않음)
- 최초 로그인 시 온보딩 화면에서 **실명·전화번호를 필수 입력**받는다 (전화번호 형식 검증)
- 온보딩 미완료는 별도 회원 상태가 아니다 — `PENDING` 상태에서 **프로필(이름·전화번호) 입력 여부**로 판정한다
- 관리자 승인 목록에는 **프로필이 입력된 PENDING 회원만** 노출한다
- 회원 관리·식별의 기준은 **이름 + 전화번호**다
- 비즈앱 전환·동의항목 심사 통과 후 카카오 자동 수집(온보딩 폼 자동 채움)은 v2 (D-025)

### 5.2 승인·거절·상태 전이 (D-034)

- **승인**: 관리자가 승인하면 `PENDING` → `ACTIVE`
- **거절**: 별도 상태를 추가하지 않는다 — `PENDING` → `INACTIVE` 전환 + **거절 사유 기록**
- 거절된 회원이 재로그인하면 **거절 안내 화면 대상으로 식별**된다 (기능 접근은 §5 상태 규칙에 따라 불가)
- **재신청**: 회원 셀프 재신청은 없다 — 관리자가 상태를 `PENDING`으로 되돌리는 운영 방식
- **승인 취소**: 별도 기능 없이 관리자의 상태 변경(`ACTIVE` → `ON_LEAVE`/`INACTIVE`)으로 갈음한다

## 6. 출석 체크

- **모든 수업**(저녁반/예약제/1:1)에 대해 관리자가 타임별 참여자 명단을 체크한다.
  - **예약제/1:1**: 예약자 명단에 대해 출석/불참을 체크한다 (체크 전 = 미체크)
  - **저녁반**: 예약이 없으므로 관리자가 회원 검색으로 명단에 추가하며, **추가됨 = 출석**이다
    (불참 상태 없음 — D-127)
- 출석 기록은 **차감과 무관한 참고용 데이터**다. (차감은 예약 시점에 이미 확정)
  - 예약했지만 불참한 경우: 차감 유지 + 출석 기록만 불참
  - 목적: 명단 관리, 참여율 확인, 횟수 문의 대응
- 예외적으로 저녁반 0.5회 차감(§4.2)만 출석 확인과 함께 관리자가 수동 처리한다.
- **소급 입력·수정을 허용한다.** 단, **소급 출석이 이미 실행된 2주 미사용 차감(`INACTIVITY`)을
  되돌리지 않는다** — 기준일 반영은 다음 배치 실행부터다 (D-127). 정정이 필요하면 관리자가
  수동 가감(`ADMIN_ADJUST`, §4.2a)으로 복구한다.
- 2주 미사용 차감(§4.3)의 기준일 중 "마지막 출석일"은 이 출석 기록 중 **출석(`ATTENDED`)만**
  기준으로 한다 — 불참은 미사용이다
  (기준일은 마지막 예약의 수업일과 비교해 더 최근 날짜를 쓴다 — §4.3).

## 7. 휴강 처리

- 관리자가 특정 날짜의 특정 수업을 휴강 처리할 수 있다 (공휴일, 이벤트 등)
- 휴강 시: 해당 타임 기존 예약 전부 자동 취소 + 차감 복구 + 알림 생성
- 휴강된 타임은 회원 예약 화면에서 예약 불가로 표시

## 8. 동시성 요구

- 정원 마지막 자리에 대한 동시 예약, 1:1 슬롯에 대한 동시 예약에서 **초과 예약 0건**
- DB 유니크 제약 + 락(또는 조건부 insert)으로 보장하고, JVM `ExecutorService`+`CountDownLatch`
  동시성 통합테스트로 검증한다 (D-098).
