# Flyway 마이그레이션 절차

## 절대 금지

- **이미 커밋된 마이그레이션 파일을 수정하지 않는다.** Flyway가 체크섬을 비교해 기동을 막는다.
  잘못됐으면 **새 버전을 추가해서 고친다**
- `ddl-auto`를 `validate` 외의 값으로 바꾸지 않는다 (스키마 주체는 Flyway 하나)
- 마이그레이션 없이 엔티티만 추가하지 않는다 (`validate`가 기동 시 실패시킨다 — 그게 정상 동작이다)

## 1. 파일 만들기

```
src/main/resources/db/migration/V<다음번호>__<소문자_스네이크_설명>.sql
```

- 번호는 건너뛰지 않고 순차 (`V2__create_member.sql`, `V3__add_pass_tables.sql`)
- 현재 최신 번호 확인: `ls src/main/resources/db/migration/`

## 2. 스키마 작성 규약

- 테이블·컬럼은 `snake_case`, 테이블명은 단수 (`member`, `session_pass`, `pass_transaction`)
- PK: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- 횟수 컬럼: `DECIMAL(4,1) NOT NULL` (D-016 — 0.5 단위)
- enum 저장은 `VARCHAR(N) NOT NULL` (코드에서 `@Enumerated(EnumType.STRING)`)
- 타임스탬프는 `TIMESTAMPTZ`, 날짜는 `DATE`, 시각은 `TIME` (conventions.md §5)
- FK는 명시적으로 선언하고 이름을 준다: `CONSTRAINT fk_reservation_member FOREIGN KEY ...`
- `NOT NULL` 여부를 엔티티의 Kotlin nullability와 반드시 일치시킨다
- 확장 전제(requirements §1): 핵심 테이블에는 `branch_id`를 둔다

## 3. 동시성 방어 제약 (D-021 — 빠뜨리기 쉬움)

policies.md §8 "초과 예약 0건"은 애플리케이션 코드로 보장할 수 없다. 제약을 먼저 건다.

- 1:1 레슨: 해당 `class_session`에 예약이 1건만 존재하도록 유니크 제약
- 같은 회원의 같은 타임 중복 예약 방지: `UNIQUE (class_session_id, member_id)`
- 조회 패턴에 맞는 인덱스도 같은 마이그레이션에 넣는다 (주간 보드 = 날짜 범위 조회)

## 4. 검증 (건너뛰지 말 것)

```bash
./gradlew ktlintFormat  # 엔티티도 함께 만들었다면 포맷 먼저
./gradlew build         # Testcontainers가 빈 DB에서 전 마이그레이션을 재생 + 엔티티 매핑 validate
```

- [ ] 통합테스트 통과 = 마이그레이션이 실제로 적용되고 엔티티 매핑이 스키마와 일치함
- [ ] 로컬 DB에도 적용해 확인: `docker compose up -d && ./gradlew bootRun`
- 로컬 DB가 이미 어긋났으면 초기화: `docker compose down -v && docker compose up -d`
  (개발 데이터만 있을 때. 데이터를 지운다는 걸 사용자에게 먼저 알린다)

## 5. 커밋

- 마이그레이션 + 엔티티 + 테스트를 같은 커밋에 (스키마와 코드가 항상 함께 이동해야 한다)
