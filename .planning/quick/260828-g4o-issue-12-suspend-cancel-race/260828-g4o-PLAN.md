# 휴강 캐스케이드 × 이용권 등록취소 경합 (이슈 #12 / WR-02)

## 문제

`AdminScheduleService.suspend()`는 ④단계에서 활성 예약을 배치 조회하며
`ReservationCancellationSnapshot.passStatus`를 **한 번만** 떠 두고, ⑤단계 루프에서 그
**낡은(stale) 값**으로 `ReservationRefundPolicy.shouldRestore`를 판정한다.

스냅샷을 뜬 뒤 ~ 복구를 반영하기 전에 다른 관리자가 같은 이용권을 등록취소
(`AdminPassService.cancel`)하면:

| 시점 | 휴강 트랜잭션 | 등록취소 트랜잭션 |
|---|---|---|
| t1 | ④ 스냅샷: `passStatus = ACTIVE` | |
| t2 | | `cancelIfNotCanceled` → `status = CANCELED` 커밋 |
| t3 | ⑤ `shouldRestore(ACTIVE, true) = true` → `adjustRemainingCount` | |
| t4 | `where status = ACTIVE` 불일치 → **0행** → `IllegalStateException` | |
| t5 | 전역 핸들러 → **500** → 휴강 전체 롤백 | |

데이터 정합성 자체는 안전하다(원자 롤백 — 부분 반영이 남지 않는다). 문제는 **무관한 동시
작업 하나 때문에 정상적인 휴강 요청이 500으로 실패**한다는 것이다.

### 왜 재조회만으로는 부족한가 (두 방향을 모두 고치는 이유)

t3의 조건부 UPDATE는 PostgreSQL READ COMMITTED에서 상대 트랜잭션이 **아직 커밋되지 않았으면**
그 행 잠금을 기다렸다가, 깨어난 뒤 갱신된 행으로 `WHERE`를 재평가한다 → 여전히 0행이 나온다.
즉 "직전 재조회"는 창을 좁힐 뿐 닫지 못한다. 그래서 캐스케이드 경로에는 **0행 = 스킵**이라는
최종 방어가 함께 있어야 한다.

## 설계 결정

### 결정 1 — 캐스케이드 전용 복구 메서드를 새로 만든다 (플래그·반환값 분기가 아니라)

`ReservationLedgerSupport`에 `restorePassAfterSuspension(...)`을 **별도 메서드**로 추가하고,
기존 `restorePassAfterCancellation`(단일 취소 경로)의 `IllegalStateException` 의미는 그대로 둔다.

기각한 대안과 이유:

- **`cascade: Boolean` 플래그 추가** — 한 메서드가 같은 0행에 대해 "예외"와 "스킵" 두 의미를
  갖게 된다. 호출부가 플래그를 잘못 넘기면 조용히 복구가 사라진다.
- **`Boolean` 반환 + 예외를 호출자 책임으로 이동** — `ReservationRefundPolicy` KDoc이 이미
  명시적으로 금지한 형태다: *"호출부가 반환값을 보고 즉흥적으로 나누게 하면 그 분기 자체가
  버그의 원인이 된다"*. 이 결정을 이번 수정이 뒤집을 이유가 없다.

메서드가 둘이면 **시그니처 자체가 실패 의미를 말한다** — `restorePassAfterCancellation`은
`Unit` + 예외(단일 취소는 복구 실패가 곧 요청 실패), `restorePassAfterSuspension`은 `Unit` +
WARN 로그(휴강은 N건 중 1건의 복구 실패가 나머지 N-1건을 롤백시킬 이유가 없다).

### 결정 2 — 캐스케이드는 "직전 재조회 + 0행이면 스킵·WARN"

`restorePassAfterSuspension`은 (a) 복구 직전 `passRepository.findById(passId)`로 **현재**
상태를 읽어 `shouldRestore`를 재판정하고, (b) 그럼에도 `adjustRemainingCount`가 0행이면
WARN 로그 후 스킵한다. 이때 잔여도 이력도 남기지 않는다 — 등록취소가 이미
`REGISTRATION_CANCELED`로 잔여를 0으로 상쇄했으므로, 여기서 복구하면 D-059의 취소 의미가
깨진다(`ReservationRefundPolicy` KDoc과 동일 근거).

**409로 거부하지 않는 이유:** 휴강은 관리자가 "이 수업을 닫는다"고 결정한 운영 행위이고, 그
결정의 성패가 *무관한 다른 회원의* 이용권 상태에 좌우되면 안 된다. 409를 주면 관리자는
재시도하는 것 말고 할 수 있는 일이 없고(자기가 고칠 수 있는 입력 오류가 아니다), 재시도 사이에
또 다른 이용권이 취소되면 같은 실패가 반복된다.

### 결정 3 — 등록취소는 상태 전환 직후 활성 예약을 한 번 더 본다

`AdminPassService.cancel`의 D-089 선행 검사는 검사~상태 전환 사이에 창이 있다. 그 사이에
예약이 **커밋**되면 취소가 그대로 통과해 "활성 예약이 달린 CANCELED 이용권"이 남는다.
`cancelIfNotCanceled` 직후(= 이 트랜잭션이 이용권 행 잠금을 확보한 뒤) 같은 검사를 반복하면,
그 창에서 커밋된 예약을 확실히 보게 되어 `PassHasActiveReservationException`으로 롤백한다.

  <action>
**1) `ReservationLedgerSupport`에 캐스케이드 전용 메서드 추가**

`restorePassAfterSuspension(passId: Long, reservationId: Long, canceledAt: OffsetDateTime, admin: Admin)`을
새로 만든다. 파라미터를 이렇게 좁히는 이유 — 휴강은 항상 복구 요청이고(`refundRequested = true`
고정), 이력 주체는 항상 관리자다(`member = null` 고정), 사유는 항상
`TransactionReason.CLASS_CANCELED_REFUND`다(D-097). 호출부가 다르게 넘길 여지를 남기지 않는다.
`reservationId`는 WARN 로그의 추적 정보로만 쓴다.

동작 순서:
1. `passRepository.findById(passId)`로 **현재** 상태를 읽는다(결정 2-a). 없으면
   `PassNotFoundException(passId)` — 기존 메서드와 동일.
2. `ReservationRefundPolicy.shouldRestore(현재상태, refundRequested = true)`가 false면 아무것도
   하지 않고 반환한다. 판정 자체는 재구현하지 않고 기존 `object`를 그대로 재사용한다.
3. `passRepository.adjustRemainingCount(passId, ReservationPassPolicy.DEDUCTION_AMOUNT)`가 0이면
   **예외 대신** WARN 로그 후 반환한다(결정 2-b). 로그에는 `passId`·`reservationId`와
   "등록취소와 동시 발생 — 정책상 복구하지 않음"이라는 의미가 드러나야 한다.
4. 0이 아니면 `passRepository.findById(passId)`로 다시 조회한 **영속** 엔티티로
   `PassTransaction(reason = CLASS_CANCELED_REFUND, member = null, admin = admin,
   amount = DEDUCTION_AMOUNT, occurredAt = canceledAt)`을 저장한다. 2번의 findById가 필요한
   이유는 `adjustRemainingCount`가 `clearAutomatically = true`라 1번에서 읽은 엔티티가 준영속이
   되기 때문이다(기존 메서드와 동일한 함정 — KDoc에 한 줄로 남긴다).

로거는 이 저장소 관례대로 `companion object { private val logger = LoggerFactory.getLogger(...) }`로
둔다(`TokenService`·`AdminSeeder`와 동일).

KDoc에 다음을 반드시 적는다: ① 왜 별도 메서드인가(결정 1의 기각 대안 2개 포함),
② 재조회를 해도 0행이 날 수 있는 이유(READ COMMITTED 재평가), 그래서 스킵이 최종 방어라는 것.

**2) `restorePassAfterCancellation`은 단일 취소 전용으로 굳힌다**

`reason: TransactionReason = CANCEL_REFUND` 파라미터를 **제거**한다 — 비기본값을 넘기던 유일한
호출부(휴강)가 새 메서드로 이동하므로, 남겨두면 "여기로도 휴강을 부를 수 있다"는 오해가 남는다.
0행 → `IllegalStateException` 동작과 메시지는 **그대로 둔다**. KDoc에 "휴강 캐스케이드는
[restorePassAfterSuspension]을 쓴다 — 여기서의 0행은 요청 실패다"를 명시한다.

**3) `AdminScheduleService.suspend` 호출부 교체**

⑤ 루프에서 `restorePassAfterCancellation(...)` 호출을
`reservationLedgerSupport.restorePassAfterSuspension(passId = snapshot.passId,
reservationId = snapshot.reservationId, canceledAt = now, admin = admin)`로 바꾼다.

`ReservationCancellationSnapshot`에서 `passStatus` 필드를 **제거**한다 — 이 값이 stale이라는 것이
이 이슈의 원인이므로 남겨두면 다시 쓰인다. 데이터 클래스 KDoc과 `suspend`의 ⑤ 단계 설명을
"복구 판정은 스냅샷이 아니라 복구 직전 현재 상태로 한다"로 갱신하고, 파일 상단 미사용 import
(`PassStatus`·`TransactionReason` — KDoc 링크가 남아 있으면 유지)를 정리한다.
`findAllByClassSessionIdAndStatusWithPass`의 fetch join은 그대로 둔다(`pass.id`를 N+1 없이 읽는다).

**4) 테스트 — 결정적 재현을 채택한다**

`ClassSessionSuspensionTest`에 테스트 1건 추가:
`휴강 도중 대상 이용권이 등록취소되면 그 건만 복구를 건너뛰고 휴강은 성공한다`.

실제 스레드 2개로 t1~t4 순서를 맞추는 것은 창이 마이크로초 단위라 **비결정적(플레이키)**이다.
이 파일에는 이미 같은 이유로 `@MockitoSpyBean reservationRepository`를 쓴 선례
(`휴강 도중 회원이 먼저 취소한 건은 취소 건수에서 제외된다`)가 있으므로 그 방식을 따른다 —
`willAnswer`로 `cancelByAdminIfActive`의 **첫 호출 때만** ⓐ
`TransactionTemplate(transactionManager).apply { propagationBehavior = PROPAGATION_REQUIRES_NEW }`
안에서 `passRepository.cancelIfNotCanceled(대상 passId, ...)`로 등록취소를 **커밋**하고 ⓑ
`invocation.callRealMethod()`로 실제 취소를 위임한다. 스냅샷(④)은 이미 뜬 뒤이고 복구(⑤)는
아직이므로 t1~t4가 정확히 재현된다. 서비스 계층(`AdminPassService.cancel`)이 아니라
리포지토리를 직접 부르는 이유는, Task 2의 이중 검사가 활성 예약을 이유로 그 경로를 막기 때문이다
— 재현하려는 것은 "취소가 어떻게 일어났는가"가 아니라 "이용권이 CANCELED가 된 상태"다.
Mockito 매처는 쓰지 않고 실제 값을 그대로 넘긴다(Kotlin non-null 파라미터 + Mockito 5 NPE 회피,
이 저장소 기존 관례).

단언: ① `suspend()`가 예외 없이 반환하고 세션이 `CANCELED`, ② `canceledReservationCount`는
실제 취소된 건수와 일치, ③ 취소된 이용권의 `remainingCount`가 변하지 않고 그 pass의
`CLASS_CANCELED_REFUND` 이력이 0건, ④ 다른 회원의 정상 이용권은 +1.0 복구 + 이력 1건.
`@MockitoSpyBean` KDoc의 "스파이인 이유는 ... 하나뿐이다" 문장을 2건으로 갱신한다.

새 파일 `src/test/kotlin/com/goldwrestling/reservation/ReservationLedgerRestoreTest.kt`에
단일 취소 경로 회귀 방어 1건 추가:
`단일 취소 복구는 이용권이 등록취소돼 있으면 IllegalStateException을 던진다`.
DB에는 CANCELED인 pass를 두고, `restorePassAfterCancellation`에 `passStatus = ACTIVE`(stale
스냅샷 상황)를 넘겨 `IllegalStateException`을 단언한다. `ReservationLedgerSupport`는 자체
트랜잭션 경계를 열지 않는 헬퍼이므로 `TransactionTemplate(transactionManager)` 안에서 호출한다
(`ClassSessionSuspensionTest`의 `createReservation` 직접 호출 선례와 동일 — 안 그러면
`TransactionRequiredException`이 난다). 애노테이션 조합은 `PassCancellationConcurrencyTest`와
동일하게(`@SpringBootTest` + `@Import(TestcontainersConfiguration, TestClockConfiguration)`,
클래스 레벨 `@Transactional` 없음) 맞춰 컨텍스트 캐시를 공유하고, 만든 데이터는 `@AfterEach`에서
`JdbcClient`로 직접 지운다(conventions §10.1). CANCELED pass 픽스처는 상태를 직접 대입하지 말고
`passRepository.cancelIfNotCanceled` 실제 취소 경로로 만든다 — `ck_pass_cancellation`(V4)이
취소 메타데이터 완전성을 강제한다.

`AdminPassService.cancel`에서 `cancelIfNotCanceled` 반환값 검사(`PassAlreadyCanceledException`)
**직후**, `zeroRemainingCount` 호출 **이전**에
`reservationRepository.existsByPassIdAndStatus(passId, ReservationStatus.ACTIVE)`를 한 번 더
확인하고 `true`면 `PassHasActiveReservationException()`을 던진다.

`zeroRemainingCount`보다 앞에 두는 이유를 코드 주석 1~2줄로 남긴다 — 뒤에 두면 그 사이 예약이
잔여를 차감해 `zeroRemainingCount`가 0행을 반환하고, 실제 원인(활성 예약)이
`PassStateConflictException`("잔여가 방금 변경되어…")로 잘못 보고된다.

`cancel`의 KDoc에 이중 검사를 추가한다: D-089 선행 검사는 정확한 실패 사유를 주기 위한 것이고,
