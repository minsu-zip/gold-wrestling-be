## 피드백 지연 (이 플랜의 검증 속도)

이 phase의 다른 태스크들은 30~60초 안에 결과가 나오지만, **Task 2의 `<automated>` 검증은 의도적으로 느리다.**
그 사실을 여기 명시해 둔다 — 실행자가 "왜 이렇게 오래 걸리지"를 의심해 폴링 횟수를 줄이거나 검증을 건너뛰지 않게 하려는 것이다.

| 검증 | 커맨드 | 예상 소요 | 성격 |
|---|---|---|---|
| Task 1 (설정 단계) | `./gradlew tasks --group documentation` + `./gradlew help --task generateApiDocs` | **~5초** | 빠른 루프용. 태스크 등록·의존 관계·설정 오류만 확인 |
| Task 2 (전체 파이프라인) | `docker compose up -d && ./gradlew generateApiDocs && ...` | **최대 ~60초** (bootJar 빌드 + 앱 콜드 스타트 + 헬스 폴링 최대 60회). 실패 경로 재현까지 포함하면 **~120초** | 느린 통합 검증. 실제 스펙 산출물을 만드는 유일한 경로 |

**폴링 횟수를 줄이지 않는다.** 최대 60회(1초 간격)는 콜드 스타트가 느린 환경에서도 파이프라인이 성공하게 하는 여유값이다.
줄이면 CI/저사양 환경에서 "간헐적으로 실패하는 태스크"가 되고, 그건 사람이 검증을 신뢰하지 않게 만드는 가장 빠른 길이다.
정상 환경에서는 폴링이 몇 회 안에 끝나므로 60회가 실제 소요 시간을 늘리지도 않는다.

**빠른 개발 루프에서의 지침:** `build.gradle.kts`의 태스크 정의를 손보는 중이라면 매번 전체 파이프라인을 돌리지 말고
`./gradlew help --task generateApiDocs`(Task 1의 검증)로 **설정 단계만** 확인하면 충분하다 — 태스크 이름 오타, 잘못된
`dependsOn`/`finalizedBy` 참조, Provider API 오용 같은 설정 오류는 이 단계에서 전부 잡힌다.
전체 파이프라인 실행은 정의가 안정된 뒤 **Task 2에서 1회(성공 경로) + 1회(실패 경로)** 돌리는 것으로 계획되어 있다.
