ROADMAP Phase 2 Note가 예고한 작업 — `SecurityConfig`의 **전체 permitAll 뼈대를 실제 인가 규칙으로 교체**한다.

두 가지 함정을 의도적으로 피한다 (RESEARCH Pitfall 1, 4):
1. 커스텀 필터는 `ExceptionTranslationFilter`보다 **앞**에 있으므로 예외를 던지면 아무도 잡지 못한다 →
   필터는 실패 시 컨텍스트를 비운 채 통과시키고, 거부는 뒤의 `AuthorizationFilter`가 한다.
2. principal에 JPA 엔티티를 담으면 지연 로딩 필드 접근에서 터진다 → 값 객체만 담는다.

그리고 D-033의 핵심 노트를 여기서 실현한다: **상태는 토큰 클레임이 아니라 매 요청 DB에서 읽는다.**

Purpose: 인증·인가 배선을 한 번에 확정해 이후 플랜이 "누가 호출 가능한가"를 다시 설계하지 않게 한다.

`java.io.Serializable`을 구현할 필요는 없다(STATELESS, 세션 직렬화 없음).
KDoc에 **왜 엔티티를 담지 않는가**를 명시한다: 필터는 영속성 컨텍스트 밖에서 도는데 `Member.branch`가

`principalId`로 다시 조회한다 — 어차피 D-033 때문에 상태는 재조회해야 한다 (RESEARCH Pitfall 4).
`requireMemberId()`는 `principalType != MEMBER`이면 `IllegalStateException("회원 전용 경로에 관리자 주체가 들어왔습니다")`
같은 메시지로 던진다(사용자 대면 문구가 아니라 프로그래밍 오류 신호다 — 이 경로는 URL 인가 규칙이 이미 막는다).

**AuthenticationPrincipalResolver.kt** — `@Service`, 클래스에 `@Transactional(readOnly = true)`.

`fun resolve(principalType, principalId): AuthenticatedPrincipal?` —

**JwtAuthenticationFilter.kt** — `OncePerRequestFilter`를 상속하는 클래스.
`@Component`를 붙이지 않고 `SecurityConfig`에서 생성자 호출로 만든다 — 필터가 스프링 빈이면 서블릿
컨테이너에도 자동 등록되어 시큐리티 체인 밖에서 한 번 더 도는 문제가 생긴다. 그 이유를 KDoc에 남긴다.
생성자 주입: `JwtDecoder`, `AuthenticationPrincipalResolver`.
`doFilterInternal` 흐름:
1. `request.getHeader(HttpHeaders.AUTHORIZATION)`에서 `Bearer ` 접두를 확인하고 토큰 문자열을 뽑는다. 없으면 바로 `filterChain.doFilter(...)`
2. `try { jwtDecoder.decode(token) } catch (ex: JwtException) { ... }` — **catch 블록에서 아무것도 던지지 않는다.**
   `logger.debug`로만 남기고(토큰 값은 로그에 남기지 않는다) 컨텍스트를 비운 채 진행한다.
   실제 401 응답은 뒤의 `AuthorizationFilter` → `ExceptionTranslationFilter` → `AuthenticationEntryPoint`가 만든다
   (RESEARCH Pattern 1 — 이 규칙을 KDoc에 그대로 적는다. 임의 변형 금지)
3. `jwt.subject`를 `Long`으로 파싱하고 `jwt.getClaimAsString("principalType")`을 `PrincipalType`으로 변환한다.
   파싱·변환 실패는 예외를 밖으로 내지 않고 미인증으로 처리한다
4. `resolver.resolve(...)`가 null이면 미인증으로 진행
5. 성공 시 `UsernamePasswordAuthenticationToken(principal, null, listOf(SimpleGrantedAuthority("ROLE_" + principalType.name)))`을
   만들어 `SecurityContextHolder.getContext().authentication`에 넣는다.
   `WebAuthenticationDetailsSource`로 details를 채운다
6. 마지막에 항상 `filterChain.doFilter(request, response)`
`SecurityContextHolder`를 명시적으로 clear 하지 않는다 — 요청 종료 시 `SecurityContextPersistenceFilter` 계열이 정리한다.

**SecurityConfig.kt 교체** — 아래는 유지한다: 생성자의 `corsProperties` 주입, `csrf { it.disable() }`(STATELESS +
Bearer 헤더만 쓰므로 CSRF 공격 표면이 없다 — 이 근거를 주석으로 유지),
`cors { it.configurationSource(corsConfigurationSource()) }`와 `corsConfigurationSource()` 메서드 전체,
`sessionManagement { STATELESS }`, `httpBasic`/`formLogin`/`logout` disable.

교체·추가할 것:
- 생성자에 `jwtDecoder: JwtDecoder`, `principalResolver: AuthenticationPrincipalResolver`,
  `authenticationEntryPoint: ProblemDetailAuthenticationEntryPoint`, `accessDeniedHandler: ProblemDetailAccessDeniedHandler` 주입
- `.addFilterBefore(JwtAuthenticationFilter(jwtDecoder, principalResolver), UsernamePasswordAuthenticationFilter::class.java)`
- `.exceptionHandling { it.authenticationEntryPoint(authenticationEntryPoint).accessDeniedHandler(accessDeniedHandler) }`
- `.authorizeHttpRequests { }` 규칙을 아래 순서 그대로 작성한다 (순서가 곧 매칭 우선순위다):
  1. `requestMatchers("/api/system/**", "/actuator/health", "/actuator/info").permitAll()`
  2. `requestMatchers("/v3/api-docs", "/v3/api-docs/**", "/v3/api-docs.yaml", "/swagger-ui/**", "/swagger-ui.html").permitAll()`
     — **이 줄이 빠지면 `./gradlew generateApiDocs`(D-029)가 401로 실패해 API 계약 파이프라인이 통째로 깨진다.** 이 경고를 주석으로 남긴다
  3. `requestMatchers("/api/auth/**").permitAll()` — 로그인·토큰 갱신·로그아웃은 access 토큰 없이 호출된다
  4. `requestMatchers("/api/admin/**").hasRole("ADMIN")`
  5. `requestMatchers("/api/members/**").hasRole("MEMBER")`
  6. `anyRequest().authenticated()`
`@EnableMethodSecurity`를 붙이지 않는다 (D-040). 상태 게이트는 02-08의 `MemberStateGate`가 서비스 계층에서 담당한다 —
그 분업을 클래스 KDoc에 한 문단으로 남긴다.
클래스 KDoc의 "뼈대 단계의 보안 설정 … 모든 요청을 permitAll" 문구를 현재 규칙 설명으로 교체한다.

**SecurityFilterChainTest.kt** — `@SpringBootTest @AutoConfigureMockMvc` +
`@Import(TestcontainersConfiguration::class, TestClockConfiguration::class, SecurityFilterChainTest.TestEndpoints::class)`.
`TestEndpoints`는 `@TestConfiguration` 안에 `@RestController`를 두어 실제 도메인 컨트롤러를 오염시키지 않고
인가 규칙만 검증한다(`GlobalExceptionHandlerTest`가 쓰는 패턴 그대로).
테스트 전용 경로는 실제 규칙에 걸리도록 `/api/members/__test-secured`, `/api/admin/__test-secured`로 잡는다.
유효 토큰은 `TokenService.issueTokenPair(...)`로 만들고 `header(HttpHeaders.AUTHORIZATION, "Bearer $accessToken")`로 보낸다.

**JwtAuthenticationFilterTest.kt** — 같은 조합. 위 behavior를 검증한다.
- "만료 토큰"은 `MutableTestClock`을 `accessTokenExpiryMinutes + 1분` 앞으로 밀어 만든다
- "다른 서명키"·"alg none" 토큰은 02-03의 `JwtConfigTest`와 같은 방식으로 테스트 안에서 직접 조립한다
- "DB 상태 변경 반영"은 회원을 저장하고 토큰을 발급한 뒤, 별도 트랜잭션에서 `status`를 `INACTIVE`로 바꾸고
  같은 토큰으로 다시 호출해 테스트 컨트롤러가 받은 principal의 `memberStatus`를 확인한다 —
  이것이 D-033의 "DB 현재 상태 기준" 요구가 실제로 지켜지는지 보는 유일한 방법이다
모든 실패 응답에서 `content().contentTypeCompatibleWith(MediaType.APPLICATION_PROBLEM_JSON)`을 확인한다 —
HTML 에러 페이지가 나가면 RESEARCH Pitfall 1에 걸린 것이다.
