<objective>
회원이 서비스에 정착하는 두 경로를 만든다 — **온보딩 제출**(AUTH-05)과 **본인 프로필 조회**(MEMBER-04).
그리고 AUTH-04의 상태 게이트를 재사용 가능한 컴포넌트(`MemberStateGate`)로 확립한다 (D-040).

policies §5.1이 "온보딩 미완료는 별도 상태가 아니라 프로필 입력 여부로 판정한다"고 못박았으므로,
온보딩 API는 상태를 바꾸지 않고 `name`·`phoneNumber`만 채운다. 승인(→`ACTIVE`)은 관리자 몫이다(02-10).

D-042에 따라 **온보딩 재제출은 막는다** — 열어두면 "프로필 수정은 관리자만"(셀프 수정은 v2 PROF-01)이
온보딩 경로로 우회되고, 관리자가 회원을 식별하는 기준(이름+전화번호)이 임의로 바뀐다.

Purpose: PENDING 회원이 승인 대기 상태에서 할 수 있는 일을 정확히 두 가지로 확정한다.
Output: 상태 게이트 + 전화번호 정규화 + 온보딩·프로필 API + openapi.yaml 갱신.
</objective>

**MemberProfileService.kt** — `@Service`, 클래스에 `@Transactional(readOnly = true)`.

  3. **엔티티가 이미 온보딩 완료 상태면 다시 한 번 거부한다** — principal은 요청 시작 시점의 스냅샷이라,

  5. **`member.status`를 건드리지 않는다** (policies §5.1 — 온보딩은 상태 전이가 아니다). 이 점을 주석으로 남긴다
  6. `MyProfileResponse.from(member)` 반환 (JPA 변경 감지로 flush된다 — 별도 save 호출 불필요, 그 이유를 주석으로 남긴다)
