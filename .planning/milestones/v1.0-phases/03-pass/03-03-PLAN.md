  <behavior>
    `fun validateAdjustment(amount: BigDecimal)` — **판정만 하고 잔여를 바꾸지 않는다.** 실제 반영은
    `PassRepository.adjustRemainingCount`(조건부 UPDATE)가 한다. 검사 순서는 아래 번호 순이다.

    1. 취소된 이용권(`status == PassStatus.CANCELED`)이면 `PassAlreadyCanceledException`
    2. 기간제(`type == PassType.EVENING_MEMBERSHIP`)면 `PassTypeNotAdjustableException` — policies §4.2a "기간제는 횟수 가감 대상이 아니다"
    3. `amount`가 0이거나 0.5의 배수가 아니면 `InvalidAdjustmentUnitException` — policies §4.2a "가감 단위는 0.5"
    4. `remainingCount + amount < 0`이면 `InsufficientPassCountException` — policies §4.2a "결과 잔여가 음수가 되는 가감은 거부"
    5. 위를 모두 통과하면 아무것도 하지 않고 정상 반환

    입력 → 기대 결과 (테스트 메서드 1개당 1건):
    | 이용권 상태 | amount | 기대 |
    |---|---|---|
    | `EVENING_MEMBERSHIP`, ACTIVE | `0.5` | `PassTypeNotAdjustableException` |
    | `SESSION_PASS` 잔여 `2.0` | `0.3` | `InvalidAdjustmentUnitException` |
    | `SESSION_PASS` 잔여 `2.0` | `0` | `InvalidAdjustmentUnitException` |
    | `SESSION_PASS` 잔여 `0.5` | `-1.0` | `InsufficientPassCountException` |
    | `SESSION_PASS` 잔여 `1.0` | `-1.0` | 예외 없음 (결과 정확히 0은 허용) |
    | `SESSION_PASS` 잔여 `1.0`, `endDate` 2020-01-01 | `0.5` | 예외 없음 (만료권도 가감 가능, D-056) |
    | `LESSON_PASS` 잔여 `1.0`, CANCELED | `0.5` | `PassAlreadyCanceledException` |
    | `SESSION_PASS` 잔여 `2.0` | `BigDecimal("0.50")` | 예외 없음 (스케일이 달라도 0.5의 배수, D-016) |
    | `EVENING_MEMBERSHIP`, CANCELED | `0.3` | `PassAlreadyCanceledException` (검사 순서 증명 — 타입·단위보다 취소가 먼저) |
  </behavior>
  <implementation>
    `Pass.kt`의 companion object에 `private val HALF_SESSION = BigDecimal("0.5")`를 두고
    `amount.remainder(HALF_SESSION).compareTo(BigDecimal.ZERO) != 0`으로 단위를 판정한다.
    **`BigDecimal(0.5)`(Double 생성자)를 절대 쓰지 않는다** — 부동소수 근사값이 들어가 판정이 조용히 틀어진다(RESEARCH Pitfall 2).
    잔여 비교는 전부 `compareTo`로 한다 — `equals`는 `0.5 != 0.50`이다(D-016).
    `remainingCount`는 nullable이지만 검사 2를 통과한 시점에는 횟수제이므로 non-null이 보장된다 —
    `!!` 대신 `requireNotNull(remainingCount) { ... }`로 그 전제를 코드에 남긴다(CHECK 제약이 깨졌을 때 원인이 드러난다).
  </implementation>
</feature>
