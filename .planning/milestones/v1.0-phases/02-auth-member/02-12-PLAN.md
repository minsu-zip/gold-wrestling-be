<objective>
02-VERIFICATION.md가 남긴 유일한 Blocker(CR-01)를 닫는다.

`MemberRegistrationService.findOrCreateByKakaoId`는 `@Transactional` 메서드 **안에서**
`DataIntegrityViolationException`을 잡고 **같은 트랜잭션으로** 재조회한다. PostgreSQL은 제약 위반이
난 순간 트랜잭션을 abort하므로 catch 블록의 재조회 자체가 실패하고, 설령 조회가 됐어도 예외가
리포지토리 프록시 경계를 통과할 때 스프링이 트랜잭션을 rollback-only로 마킹해 커밋 시
`UnexpectedRollbackException`이 난다. 즉 경쟁이 실제로 발생하면 사용자는 200이 아니라 500을 받는다.

Purpose: 카카오 로그인 버튼 중복 클릭·모바일 네트워크 재시도는 실사용에서 흔하다. ROADMAP Success
Criteria 1("카카오 OAuth로 로그인하면 PENDING 상태로 가입되고 토큰이 발급된다")이 이 경로에서 깨진다.
Output: 트랜잭션 밖 재시도로 교정된 로그인 경로 + 이 경쟁을 재현하는 동시성 테스트 + 결정 기록.

    `MemberRegistrationService.findOrCreateByKakaoId`에서 `try`/`catch (e: DataIntegrityViolationException)`
    블록을 제거한다. 메서드는 `memberRepository.findByKakaoId(kakaoId)`로 기존 회원을 찾아 있으면
    `MemberSessionResponse.from(it)`을 반환하고, 없으면 `createPendingMember(kakaoId)` 결과를 감싸
    반환한다. `createPendingMember`의 `saveAndFlush`가 던지는 `DataIntegrityViolationException`은
    **잡지 않고 그대로 전파**한다 — 이 메서드의 `@Transactional` 경계가 롤백되며 끝나야 다음 호출이
    깨끗한 새 트랜잭션에서 시작될 수 있다. 더 이상 쓰이지 않는
    `org.springframework.dao.DataIntegrityViolationException` import를 이 파일에서 제거한다.
    `saveAndFlush`는 그대로 둔다 — 제약 위반이 커밋 시점이 아니라 이 메서드 안에서 드러나야 한다.

    같은 파일의 KDoc "동시 최초 로그인 경쟁 처리" 문단(현재 31~36행)을 실제 동작으로 고쳐 쓴다.
    새 문단이 담아야 할 사실: (1) 이 메서드는 경쟁을 **흡수하지 않고** `DataIntegrityViolationException`을
    전파한다, (2) 복구(재시도)는 트랜잭션을 갖지 않는 `KakaoAuthService.login`의 책임이다,
    (3) 같은 트랜잭션 안에서 재조회로 복구할 수 없는 이유 — PostgreSQL은 제약 위반 시 트랜잭션을
    abort해 이후 모든 SQL이 "current transaction is aborted"로 실패하고, 예외가 리포지토리 프록시
    경계를 넘으면 스프링이 rollback-only로 마킹해 커밋에서 `UnexpectedRollbackException`이 난다.

    `KakaoAuthService.login`에서 `memberRegistrationService.findOrCreateByKakaoId(kakaoId)` 호출을
    `try`/`catch (e: DataIntegrityViolationException)`로 감싸고, catch에서 같은 메서드를 **정확히 한 번**
    다시 호출해 그 결과를 쓴다. 재시도 결과가 또 실패하면 그 예외를 그대로 전파한다(무한 재시도 금지 —
    두 번째 호출 시점에는 경쟁 상대의 INSERT가 이미 커밋되어 있으므로 조회로 끝난다).
    `org.springframework.dao.DataIntegrityViolationException` import를 추가한다.
    이 재시도가 왜 새 트랜잭션이 되는지를 KDoc(또는 인라인 주석)에 한 문단으로 남긴다:
    `KakaoAuthService`에는 트랜잭션 애노테이션이 없어 각 `findOrCreateByKakaoId` 호출이 프록시를 거쳐
    독립된 트랜잭션을 시작하고, 첫 호출의 실패 트랜잭션은 이미 롤백되어 두 번째 호출에 영향을 주지 않는다.
    `login`에 `@Transactional`을 붙이지 않는다 — 붙이는 순간 두 호출이 같은 트랜잭션에 참여해
    이 수정 자체가 무의미해지고, conventions §7(트랜잭션 안 외부 API 호출 금지)도 위반한다.

    `src/test/kotlin/com/goldwrestling/auth/KakaoLoginConcurrencyTest.kt`를 새로 만든다.

    애노테이션 조합은 `KakaoAuthControllerTest`와 **완전히 동일하게** 유지한다:
    `@SpringBootTest`, `@AutoConfigureMockMvc`,
    `@Import(TestcontainersConfiguration::class, TestClockConfiguration::class)`,
    필드에 `@MockitoBean private lateinit var kakaoApiClient: KakaoApiClient`.
    **단 `@Transactional`은 붙이지 않는다** — 각 스레드가 별도 트랜잭션이어야 경쟁이 재현된다
    (add-domain-test §2·§4). 애노테이션이 하나라도 다르면 스프링이 컨텍스트를 새로 띄워 전체 테스트가
    느려지므로, `@AutoConfigureMockMvc`는 MockMvc를 쓰지 않더라도 캐시 키를 맞추기 위해 유지한다.

    주입받을 빈: `KakaoAuthService`, `MemberRepository`, `Clock`,
    `org.springframework.jdbc.core.simple.JdbcClient`.

    카카오 스텁: `KakaoAuthControllerTest`의 스텁 헬퍼와 같은 방식으로
    `given(kakaoApiClient.exchangeToken(anyString()))` 과 `given(kakaoApiClient.fetchKakaoId(anyString()))`
    를 고정 응답으로 세팅한다. 스텁은 각 테스트 시작 시 `@BeforeEach`가 아니라 테스트 본문 앞에서
    설정해도 되지만, kakaoId는 테스트마다 다른 값(예: 7001L, 7002L)을 쓴다 — 정리 누락 시
    다른 테스트를 오염시키지 않게 하기 위해서다.

    경쟁 재현: `threads = 4`, `Executors.newFixedThreadPool(threads)`,
    `CountDownLatch startLatch = CountDownLatch(1)` + `CountDownLatch doneLatch = CountDownLatch(threads)`.
    각 작업은 `startLatch.await()`로 대기했다가 동시에 `kakaoAuthService.login("동시-로그인-코드")`를
    호출하고, 성공은 `AtomicInteger` 증가 + 반환된 memberId를 동기화된 컬렉션(예:
    `Collections.synchronizedList`)에 담고, 예외는 동기화된 리스트에 수집한 뒤 `finally`에서
    `doneLatch.countDown()`. `startLatch.countDown()` 으로 출발시키고 `doneLatch.await(30, SECONDS)`가
    true인지 확인한 뒤 executor를 `shutdown()`한다.
    스레드 수를 4로 잡은 이유를 주석 한 줄로 남긴다: 경쟁 중 스레드가 유니크 인덱스 대기로 커넥션을
    붙잡으므로 기본 커넥션 풀 크기 안에서 안전하게 재현되는 최소 규모다.

    DB 실제 행 수 검증은 JPA 캐시를 우회하도록 `JdbcClient`로 직접 센다:
    `select count(*) from member where kakao_id = :kakaoId`.

    `@AfterEach` 정리(필수): 이 테스트는 `@Transactional` 롤백을 쓸 수 없으므로 직접 지운다.
    **외래키 순서상 refresh_token을 먼저 지우고 member를 지운다.** JdbcClient로
    `delete from refresh_token where member_id in (select id from member where kakao_id in (:ids))`,
    이어서 `delete from member where kakao_id in (:ids)`. 이 정리를 빠뜨리면 남은 member 행이
    `KakaoAuthControllerTest`의 `assertEquals(1, memberRepository.count())` 같은 전체 건수 단언을
    깨뜨린다 — 정리가 왜 필수인지 주석으로 남긴다.

    테스트 메서드명은 백틱 한국어 서술문으로 쓴다(conventions §10.2).
  </action>
