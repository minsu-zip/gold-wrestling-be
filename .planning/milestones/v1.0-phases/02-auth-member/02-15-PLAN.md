<objective>
02-REVIEW.md WR-06을 닫는다.

서버는 `keyword`·`status`·`onboardingCompleted`·`page`·`size`를 `@ModelAttribute`로 **평평한 쿼리
파라미터**로 바인딩하지만, 생성된 `docs/api/openapi.yaml`은 이를
`name: condition, in: query, schema: $ref MemberSearchCondition` — **객체 파라미터 1개**로 기술한다.
OpenAPI 기본 해석(`style: form, explode: true`)으로는 등가지만, 객체 파라미터를
`deepObject`(`condition[keyword]=...`)나 JSON 문자열로 직렬화하는 생성기·클라이언트가 흔하다.
그렇게 되면 서버는 파라미터를 **전혀 바인딩하지 못한다** — 검색·상태 필터·페이지네이션이 조용히
무시되고 항상 전체 1페이지가 나간다.

Purpose: `openapi.yaml`은 FE와의 유일한 계약이다(D-013, CLAUDE.md 규칙 4 — FE가 이 파일로 타입을
생성한다). 해석이 갈리는 표현을 계약에 남겨 두면 통합 시점에 원인 찾기 어려운 버그가 된다.
Output: `@ParameterObject`로 펼쳐진 계약 + 재생성된 openapi.yaml + 결정 기록.

AdminMemberController.search (수정 대상, 현재 형태)
```
@GetMapping
@Operation(summary = "회원 목록 조회 (검색·상태 필터·페이지네이션. status=PENDING+onboardingCompleted=true 가 승인 대기 목록)")
fun search(@ModelAttribute @Valid condition: MemberSearchCondition): PageResponse<MemberSummaryResponse>
```

MemberSearchCondition (data class, 변경 없음) — 필드와 기본값
- `keyword: String? = null`
- `status: MemberStatus? = null`
- `onboardingCompleted: Boolean? = null`
- `page: Int = 0`   (`@field:Min(0)`)
- `size: Int = 20`  (`@field:Min(1)`, `@field:Max(100)`)
각 필드에 `@field:Schema(description = ...)` 가 이미 붙어 있다 — 펼쳐진 뒤에도 설명이 유지되어야 한다.

현재 openapi.yaml의 해당 부분 (docs/api/openapi.yaml, `/api/admin/members` get)
```
      parameters:
      - name: condition
        in: query
        required: true
        schema:
          $ref: "#/components/schemas/MemberSearchCondition"
```

  <action>
    `AdminMemberController.search`의 `condition` 파라미터에 springdoc의 `@ParameterObject`를 추가한다.
    최종 형태는 `@ParameterObject @ModelAttribute @Valid condition: MemberSearchCondition` 이다 —
    `@ModelAttribute`·`@Valid`는 **제거하지 않는다**. `@ParameterObject`는 스펙 생성 힌트일 뿐
    런타임 바인딩에는 관여하지 않으므로, 이 변경으로 서버 동작이 바뀌면 안 된다.

    **임포트 경로를 추측하지 않는다(CLAUDE.md 규칙 9).** springdoc 3.0.3 기준
    `@ParameterObject`의 정확한 패키지를 verify-boot4-api 스킬 절차로 확인한 뒤 적용한다:
    ① context7 MCP로 springdoc 문서 조회, 또는
    ② `./gradlew dependencies --configuration compileClasspath | grep springdoc` 로 실제 아티팩트를 찾고
       `unzip -l`(또는 `jar tf`)로 클래스 경로를 확인.
    확인 방법과 결과 경로를 SUMMARY에 한 줄로 남긴다.

    KDoc(또는 파라미터 위 주석)에 `@ParameterObject`를 붙인 이유를 남긴다: 이 애노테이션이 없으면
    springdoc이 조건 DTO를 `name: condition` 객체 파라미터 하나로 기술하고, 그 표현을 `deepObject`나
    JSON 문자열로 직렬화하는 FE 생성기에서는 서버가 파라미터를 전혀 바인딩하지 못한다.

    이어서 openapi.yaml을 재생성한다 (add-endpoint §6):
    `docker compose up -d` → `./gradlew generateApiDocs`.
    재생성 후 `git diff docs/api/openapi.yaml` 로 **의도한 변경만** 들어갔는지 확인한다.
    기대 diff: `/api/admin/members` get의 `parameters`가 `condition` 하나에서
    `keyword`/`status`/`onboardingCompleted`/`page`/`size` 5개로 바뀌고, 각각 `in: query`,
    `required: false`, 원래 필드의 `description`·기본값이 유지된다.
    `servers:` 가 `/` 로 유지되는지도 확인한다(환경 정보가 박히면 안 된다).
    그 밖의 경로가 함께 바뀌었다면 원인을 밝히고 SUMMARY에 기록한다.

    `components.schemas.MemberSearchCondition` 정의가 더 이상 참조되지 않아 스펙에서 사라질 수 있다 —
    사라지는 것 자체는 정상이다. 다만 다른 곳에서 참조 중이면 재생성 결과에 남는다. 어느 쪽인지
    diff로 확인해 SUMMARY에 적는다.
