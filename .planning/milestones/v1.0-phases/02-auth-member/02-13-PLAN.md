<objective>
02-REVIEW.md WR-01을 닫는다. 그리고 그 과정에서 드러난 두 번째 결함(재사용 감지의 대량 폐기가
예외와 함께 롤백되어 **실제로는 DB에 남지 않는 문제**)을 함께 닫는다.

결함 1 (TOCTOU): `TokenService.rotate()`는 행을 읽고(`findByTokenHash`) → 메모리에서 `isRevoked()`를
판단하고 → 더티체킹으로 `revokedAt`을 채운다. READ COMMITTED에서 같은 refresh 토큰이 동시에 두 번
제시되면 두 트랜잭션 모두 "미폐기"를 읽고 둘 다 회전에 성공한다. 토큰 하나에서 유효한 refresh 두 개가
파생되고, D-036이 약속한 재사용 감지(탈취 감지)가 **정확히 탈취 시나리오**에서 발동하지 않는다.

결함 2 (폐기 롤백): 재사용이 감지되면 `revokeAllUsableFor(...)` 후 `RefreshTokenInvalidException`을
던진다. 이 예외는 `DomainException` → `RuntimeException` 이라 스프링 기본 롤백 규칙에 걸려
**폐기가 통째로 롤백된다.** 기존 `RefreshTokenRotationTest`가 이를 잡지 못한 이유는 테스트 클래스에
`@Transactional`이 붙어 있어 서비스가 테스트 트랜잭션에 참여하고, 단언이 커밋 후 DB가 아니라
같은 영속성 컨텍스트의 메모리 상태를 보기 때문이다. 만료 경로의 `existing.revoke(now)`도 같은 문제다.

Purpose: D-036이 명시한 "폐기된 토큰 재제시 → 전체 폐기"는 탈취 대응 통제다. 지금은 그 통제가
경쟁 상황에서 발동하지 않고, 발동해도 저장되지 않는다.
Output: 조건부 UPDATE 기반 원자적 폐기 + 실패 응답에서도 폐기가 커밋되는 트랜잭션 규칙 + 동시성/지속성 테스트.

    3. `fun revokeAllUsableByAdminId(adminId: Long, now: OffsetDateTime): Int`

  <action>
    `TokenService.rotate`의 애노테이션을
    `@Transactional(noRollbackFor = [RefreshTokenInvalidException::class])`로 바꾼다.
    이유를 KDoc에 명시한다: 재사용 감지·만료 처리는 **실패 응답을 주면서도 폐기 사실은 남겨야 하는**
    경로인데, `RefreshTokenInvalidException`이 `RuntimeException`이라 기본 롤백 규칙에 걸려 폐기가
    통째로 사라진다. 이 규칙이 없으면 D-036의 재사용 감지는 로그만 남기고 실제 폐기는 하지 않는다.
    `rotate`는 폐기 외의 상태를 바꾸지 않으므로 실패 시 커밋해도 부분 반영 위험이 없다는 점도 함께 적는다.

    `rotate` 본문을 다음 순서로 다시 쓴다:
    1. `refreshTokenRepository.findByTokenHash(hash(rawRefreshToken))` — null이면 `RefreshTokenInvalidException`.
    2. **벌크 UPDATE를 호출하기 전에** `existing.id!!`, `existing.principalType()`, `existing.principalId()`,
       `existing.isRevoked()`, `existing.isExpired(now)` 를 지역 변수(val)에 담는다.
       `clearAutomatically = true`가 영속성 컨텍스트를 비우면 `existing`이 준영속 상태가 되어
       LAZY 연관(`member`/`admin`) 접근이 `LazyInitializationException`으로 터진다 — 이 순서가
       왜 중요한지 인라인 주석 한 줄로 남긴다.
    3. 이미 폐기된 것이 명확하면(스냅샷 `isRevoked()`가 true) 기존과 같이 재사용 로그를 남기고
       `revokeAllUsableFor(principalType, principalId, now)` 호출 후 `RefreshTokenInvalidException`.
    4. 만료됐으면 `refreshTokenRepository.revokeIfUsable(id, now)`를 호출(반환값은 쓰지 않음)한 뒤
       `RefreshTokenInvalidException`. 더티체킹(`existing.revoke(now)`)은 쓰지 않는다.
    5. 그 외에는 `refreshTokenRepository.revokeIfUsable(id, now)`의 반환값을 검사한다.
       **0이면 경쟁에서 졌다는 뜻 = 다른 트랜잭션이 방금 이 토큰을 폐기했다 = 재사용**이므로,
       3번과 동일하게 재사용 로그 + `revokeAllUsableFor(...)` + `RefreshTokenInvalidException`.
       0이 왜 재사용 신호인지 인라인 주석으로 남긴다.
    6. 정상 경로: `issueTokenPair(principalType, principalId)` 반환. (지역 변수에 담아 둔 값을 쓴다 —
       준영속이 된 `existing`을 다시 만지지 않는다)

    `revokeAllUsableFor`의 시그니처를
    `private fun revokeAllUsableFor(principalType: PrincipalType, principalId: Long, at: OffsetDateTime)`
    로 바꾸고, 본문을 `when (principalType)` 분기로 Task 1의
    `revokeAllUsableByMemberId` / `revokeAllUsableByAdminId` 호출로 교체한다.
    엔티티를 인자로 받던 기존 구현(`refreshToken.member!!` / `refreshToken.admin!!`)은 제거한다 —
    벌크 UPDATE 이후 준영속 엔티티의 LAZY 연관을 만지지 않기 위해서다.

    `revokeAllForMember`·`revoke`·`issueTokenPair`는 **변경하지 않는다**
    (`<critical_constraint>` 참고 — `AdminMemberService`가 같은 트랜잭션에서 더티 상태를 들고 호출한다).
    `findAllByMemberAndRevokedAtIsNull` / `findAllByAdminAndRevokedAtIsNull` import·사용처가
    `revokeAllForMember`에만 남는지 확인하고, 미사용 import가 생기면 정리한다.
