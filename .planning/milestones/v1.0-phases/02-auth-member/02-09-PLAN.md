**MemberSpecifications.kt** — `object`. 각 함수는 조건이 없으면 `null`을 반환하고, 호출부가
`Specification.allOf(...)` 또는 `listOfNotNull(...).reduce { a, b -> a.and(b) }` 형태로 합친다.
(Spring Data JPA 4.x / Spring Framework 7 기준으로 `Specification.where(...)`가 deprecated 되었는지
verify-boot4-api 절차로 확인한 뒤, 현재 라인에서 권장되는 조합 API를 쓴다. 추측하지 않는다.)

- `fun keywordContains(keyword: String?): Specification<Member>?`
  - blank면 null
  - 이름 조건: `criteriaBuilder.like(criteriaBuilder.lower(root.get("name")), "%${keyword.lowercase()}%")`
  - 전화번호 조건: 검색어에서 하이픈·공백을 제거한 값(`PhoneNumberNormalizer.normalize(keyword)`)으로 like.
    **저장 형식이 하이픈 없는 숫자이므로(D-041) 검색어도 같은 형식으로 정규화해야 매칭된다.** 이 이유를 KDoc에 남긴다
  - 두 조건을 `or`로 묶는다 (D-035 "검색어 하나로 이름·전화번호 부분 일치")
  - `null`인 컬럼은 SQL `LIKE`에서 자동으로 매칭되지 않으므로 별도 null 처리를 하지 않아도 되지만,
    그 사실을 주석으로 남겨 다음 사람이 불필요한 방어 코드를 추가하지 않게 한다
  - **와일드카드 이스케이프**: 검색어에 `%`나 `_`가 들어오면 의도치 않은 전체 매칭이 된다.
    `%`·`_`·`\`를 이스케이프하고 `like(..., escapeChar)` 형태를 쓴다
- `fun hasStatus(status: MemberStatus?): Specification<Member>?` — null이면 null, 아니면 `equal`
- `fun onboardingCompleted(flag: Boolean?): Specification<Member>?` — null이면 null.
  true: `name`이 not null이고 `''`가 아니며 `phoneNumber`도 동일. false: 그 조건의 부정.
  Member 엔티티의 `isOnboardingCompleted()`와 **같은 규칙**이어야 한다 — 규칙이 두 곳에 있다는 점과
  둘이 어긋나면 승인 목록이 정책과 달라진다는 점을 KDoc 경고로 남기고, Task 1 테스트가 그 정합성을 검증한다
